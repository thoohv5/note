# 存储过程是否是一个完整事务

验证存储过程（Stored Procedure）是否作为一个“整体事务”运行，是一个非常经典且重要的实验。

首先需要明确一个概念：**存储过程本身并不等同于一个事务**。默认情况下，存储过程内部的每一条 SQL 语句都会根据数据库的 `autocommit` 设置来执行。如果你希望它成为一个整体事务，通常需要显式地加上 `BEGIN TRANSACTION` 和 `COMMIT/ROLLBACK`。

为了验证这一点，我们可以通过**“故意制造失败”**的实验来观察：如果第二条语句报错，第一条语句的数据是留下了（非整体事务）还是消失了（整体事务）。

---

### 实验方案：转账失败模拟

我们将创建一个简单的账户表，并编写一个执行两次更新操作的存储过程。

### 1. 准备基础数据

```sql
CREATE TABLE accounts (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    balance DECIMAL(10, 2)
);

INSERT INTO accounts VALUES (1, 'Alice', 1000.00);
INSERT INTO accounts VALUES (2, 'Bob', 1000.00);
```

### 2. 编写验证存储过程

这个过程会尝试从 Alice 账户扣钱，然后向一个**不存在**的列或通过**触发报错**的方式向 Bob 账户加钱。

```sql
DELIMITER //

CREATE PROCEDURE test_transaction_behavior()
BEGIN
    -- 第一步：扣款成功
    UPDATE accounts SET balance = balance - 500 WHERE id = 1;
    
    -- 第二步：故意制造错误（例如访问不存在的列，或插入非法值）
    -- 这里我们尝试给一个不存在的列赋值来强制报错
    UPDATE accounts SET non_existent_column = 500 WHERE id = 2;
END //

DELIMITER ;
```

---

### 3. 执行实验与结果分析

### 情况 A：默认状态（无显式事务控制）

执行：`CALL test_transaction_behavior();`

- **现象**：你会收到一个错误提示（Unknown column 'non_existent_column'）。
- **查询数据**：`SELECT * FROM accounts;`
- **结果**：你会发现 **Alice 的余额变成了 500，而 Bob 还是 1000**。
- **结论**：存储过程默认**不是**一个整体事务。每一行代码执行完就立即提交了。

### 情况 B：添加事务控制

修改存储过程，加入事务块：

```sql
CREATE PROCEDURE test_with_transaction()
BEGIN
    DECLARE EXIT HANDLER FOR SQLEXCEPTION 
    BEGIN
        ROLLBACK; -- 捕获异常并回滚
    END;

    START TRANSACTION;
        UPDATE accounts SET balance = balance - 500 WHERE id = 1;
        UPDATE accounts SET non_existent_column = 500 WHERE id = 2; -- 报错点
    COMMIT;
END //
```

- **查询数据**：你会发现 **Alice 和 Bob 的余额都保持 1000 不变**。
- **结论**：只有显式使用了 `START TRANSACTION` 和异常处理逻辑，存储过程才能表现为“整体事务”。

---

### 核心对比表

| **特性** | **默认存储过程** | **带事务控制的存储过程** |
| --- | --- | --- |
| **原子性** | 语句级原子性（每一条单独算） | 过程级原子性（全部成功或全失败） |
| **中间状态** | 报错前的修改会永久生效 | 报错后会自动/手动回滚 |
| **适用场景** | 简单的查询或独立的数据维护 | 涉及财务、多表关联等数据一致性要求高的操作 |
