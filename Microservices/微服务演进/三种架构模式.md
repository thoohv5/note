# 三种架构模式

### 1. **数据库每服务独立（Database per Service）—— 强隔离模式**

### ✅ 特点：

- 每个微服务拥有**自己的数据库**（物理或逻辑隔离）
- 服务间 **不能直接访问对方数据库**
- 通过 API（HTTP/gRPC 等）或消息队列来通信

### 🧩 举例：

用户服务的数据库只包含用户相关表，商品服务无法直接查询这些表。

### 👍 优点：

- 高内聚、低耦合
- 易于独立部署、扩展
- 清晰的服务边界

### ⚠️ 缺点：

- 跨服务查询困难
- 数据一致性处理成本高（需要 eventual consistency、事件驱动等方式）

---

### 2. **共享数据库（Shared Database）—— 快速集成模式**

### ✅ 特点：

- 多个服务**共享一套数据库**
- 各服务直接访问自己关心的表，有时也会访问别的服务的表

### 🧩 举例：

用户服务和订单服务都访问 `users` 表，甚至 `orders` 表。

### 👍 优点：

- 实现简单
- 跨服务数据查询方便（JOIN 都能搞定）

### ⚠️ 缺点：

- 服务边界不清晰，耦合严重
- 容易产生“数据腐化”
- 难以独立演进与扩展

---

### 3. **API 组合查询（API Composition）—— 聚合层模式**

### ✅ 特点：

- 每个服务只维护自己的数据和逻辑
- 提供 API 给聚合层（如网关/BFF）调用组合数据

### 🧩 举例：

前端页面展示用户和订单信息时，通过 API Gateway 请求 `user-service` 和 `order-service`，再组合返回数据。

### 👍 优点：

- 保持服务独立性
- 灵活组合数据
- 前后端解耦清晰

### ⚠️ 缺点：

- 多服务调用造成性能下降（网络开销、延迟）
- 聚合逻辑可能变复杂
