# 模式

你提到的 `ktctl exchange` 中的 `--mode` 参数支持三种方式：`selector`、`scale`、`ephemeral`。以下是它们的详细对比和使用建议：

---

## 🔧 `-mode selector`（默认方式）

### ✅ 适用场景：

你只想 **拦截某个服务的流量**，不希望影响线上运行的 Deployment。

### ⚙️ 工作方式：

- `ktctl` 会创建一个 **shadow pod**
- 然后通过 Kubernetes 的 Service selector 和路由，将访问服务的流量 **重定向到本地服务**

### 📌 特点：

- ✅ 不会影响现有 Deployment 和 Pod
- ✅ 最安全，推荐在大多数场景下使用
- ⚠️ 要求 Service 的 selector 可以正确地匹配目标 pod

### 🧾 示例命令：

```bash
bash
复制编辑
ktctl exchange order-service --expose 3000:80 --mode selector -n default

```

---

## 🔧 `-mode scale`

### ✅ 适用场景：

你需要**完全接管 Deployment 的流量**，进行高仿真、本地替代调试（如依赖注入、自定义行为）

（⚠️ 谨慎使用于生产环境）

### ⚙️ 工作方式：

- `ktctl` 会将原来的 Deployment **scale 到 0**
- 创建一个 **新的 shadow Pod**（带代理的）
- 所有访问这个 Deployment 的请求都会经过这个 Pod 并跳转到你的本地服务

### 📌 特点：

- 🚫 会中断原有 Pod，可能影响线上流量
- ✅ 可以完整接管 service 对应的流量

### 🧾 示例命令：

```bash
bash
复制编辑
ktctl exchange order-service --expose 8080 --mode scale -n default

```

---

## 🧪 `-mode ephemeral`（实验性）

### ✅ 适用场景：

临时调试 / 实验环境快速代理，不想动 Selector 或 Deployment。

### ⚙️ 工作方式：

- 启动一个临时 Pod 作为代理
- 自动处理 Service 替代（不依赖 label selector 或 scaling）

### 📌 特点：

- 🧪 仍在试验中，不建议在正式环境使用
- ✅ 快速简单，适合快速开发验证

### 🧾 示例命令：

```bash
bash
复制编辑
ktctl exchange order-service --expose 3000:80 --mode ephemeral -n default

```

---

## ✅ 总结选择建议：

| 模式 | 安全性 | 是否影响原部署 | 使用难度 | 适用场景 |
| --- | --- | --- | --- | --- |
| `selector` | ⭐⭐⭐⭐ | 否 | ⭐⭐ | 推荐默认，非侵入式调试 |
| `scale` | ⭐⭐ | 是（会 scale 原 Deployment） | ⭐⭐⭐ | 高仿真调试，需要全量接管流量 |
| `ephemeral` | ⭐⭐ | 否 | ⭐ | 快速实验，但不稳定 |
